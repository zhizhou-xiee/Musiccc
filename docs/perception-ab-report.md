# 《借月》音乐感知 A/B 本地技术验证

日期：2026-10-14  
状态：已完成本地数据与成本代理测试；等待负责人确认默认路线

## 1. 验证范围

本轮只使用最终 MP3 母带、现有终版 MV 时间轴、人工演唱者标注和人工粗粒度乐器表。没有上传音频，没有调用模型 API，没有产生付费资源。

三组输入使用完全相同的 12 个音频段落、歌词、演唱者和时间范围：

1. `lyrics_only`：仅歌词、演唱者与段落，用作基线；
2. `candidate_a_features`：基线加 FFmpeg 离线测量的压缩声学特征；
3. `candidate_b_summaries`：基线加预生成音乐摘要。

本轮段落单位较粗，适合判断路线，不是正式 MCP 的最终推进粒度。正式版仍可拆成乐句或短段落，但不得因此引入运行时动态路由。

## 2. 候选数据

候选 A 每段包含：

- 综合响度、响度范围和真峰值；
- 三段式响度轮廓；
- 频谱质心、滚降、平坦度和频谱通量中位数；
- 自动节拍密度；
- 依据人声起止时间计算的演唱覆盖率。

候选 B 每段包含一条简短摘要，明确区分：

- 歌词、主唱与和声：人工时间轴标注；
- 乐器：人工粗粒度标注；
- 动态关系：FFmpeg 自动测量；
- 摘要状态：`draft_needs_listening_review`。

两条路线都明确说明返回的是压缩特征或摘要，不代表模型直接听见了原始音频。

## 3. 预处理成本

在当前本机对整首歌的 12 个音频段落运行：

| 项目 | 实测墙钟时间 |
| --- | ---: |
| A 与 B 共用的响度测量 | 3.850 秒 |
| 仅 A 需要的频谱测量 | 0.639 秒 |
| 数据组装与写盘 | 0.001 秒 |
| 完整实验 | 4.498 秒 |

这里没有计入人工制作或复核乐器表、摘要的时间。峰值内存未在当前沙箱中取得可靠读数，不能编造；正式 MCP 服务实现后再用固定并发回放记录 RSS、CPU 与 p95。

无论选择 A 或 B，线上请求都只读取预生成 JSON，不在网关内分析音频。因此两者的网关 CPU/内存差异预计主要来自响应大小与 JSON 序列化，而不是音频计算；这个判断仍需服务实现后的负载测试确认。

## 4. 存储与响应体积

| 方案 | 格式化 JSON | 全曲分段累计紧凑响应 | 平均单段紧凑响应 |
| --- | ---: | ---: | ---: |
| 仅歌词 | 29,900 B | 14,223 B | 1,185 B |
| A：声学特征 | 37,921 B | 19,099 B | 1,592 B |
| B：音乐摘要 | 34,340 B | 17,816 B | 1,485 B |

B 的实验产物比 A 小约 9.4%；相对仅歌词的额外响应体积，B 为 3,593 B，A 为 4,876 B，B 少约 26.3%。三者都很小，存储本身不是瓶颈。

## 5. Token 代理结果

本机没有 GPT、Claude、Gemini 对应的供应商 tokenizer，也没有调用模型 API。本轮用紧凑 JSON 的 UTF-8 字节数除以 4 至除以 3形成透明的比较区间，**不是实际计费 Token**。

| 方案 | 全曲累计 Token 代理 | 平均单段 Token 代理 | 相对仅歌词的新增 Token 代理 |
| --- | ---: | ---: | ---: |
| 仅歌词 | 3,558–4,746 | 296–396 | 0 |
| A：声学特征 | 4,778–6,370 | 398–531 | 1,220–1,624 |
| B：音乐摘要 | 4,458–5,943 | 372–495 | 900–1,197 |

B 的新增 Token 代理比 A 低约 26%。工具定义、MCP 协议包裹、用户提示和模型回答未计入；这些必须在 MCP 完成后按真实客户端 usage 再测。

## 6. 理解效果代理

本轮设计了 10 个事实问题，只检查输入是否明确包含答案所需的证据，不调用模型，也不以回答文风作为评分。结果如下：

| 方案 | 明确支持 | 部分支持 | 不支持 |
| --- | ---: | ---: | ---: |
| 仅歌词 | 4 | 0 | 6 |
| A：声学特征 | 7 | 0 | 3 |
| B：音乐摘要 | 7 | 2 | 1 |

A 的优势是可以精确比较响度、频谱质心等数值；它无法仅凭这些指标可靠识别横笛、古筝、架子鼓或主伴奏关系。B 可以直接提供人工标注的乐器、人声关系和段落变化，但不适合回答精确的频谱数值问题。

本轮还发现一项重要风险：未经人工核对的自动节拍网格在“清唱（无伴奏）”段仍统计出 31 个拍点。这个数字可能反映人声起音或检测误差，却很容易被文本模型误读为稳定伴奏节拍。它证明原始或半结构化数字并不天然等于音乐理解。

同样，B 也不是自动正确：第一次按任意时间重叠合并粗粒度乐器事件时，间奏开头的横笛被误归入前一段副歌。实验脚本已要求事件至少覆盖当前段落 10% 且不少于 1 秒，但正式摘要仍必须逐段听审。

## 7. 初步建议

建议将 **候选 B：预生成音乐摘要** 作为唯一默认音乐感知路线，理由是：

- 对乐器、人声关系和段落变化的覆盖更贴近项目目标；
- 相对 A 的新增 Token 代理低约 26%；
- 产物更小，模型不需要自行解释一组容易误读的声学数字；
- 维护重点集中在离线摘要与人工校对，不需要长期维护复杂特征解释层；
- 网关仍只读取静态数据，不增加在线音频分析负担。

候选 A 可以保留在实验目录作为对照证据，但不进入正式 MCP 响应，不做运行时切换或动态降级。

这仍是等待负责人确认的建议，不是已经批准的正式架构。真实客户端模型是否更容易正确回答问题，仍需在 Phase 4 对 GPT、Claude、Gemini 分别实测后记录。

## 8. 确认后的下一步

若负责人确认 B：

1. 将段落级摘要拆成适合 `music_next` 的乐句或短段；
2. 逐条试听母带，校对乐器、人声表现和动态描述；
3. 明确每条事实是人工标注、自动测量还是推断；
4. 实现无状态游标和四个 MCP 工具；
5. 测量真实 MCP 响应的 Token、并发、CPU、内存和客户端兼容性。
