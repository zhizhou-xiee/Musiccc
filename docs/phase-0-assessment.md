## 3. 最小可行架构

### 3.1 单一轻量应用服务

建议使用 TypeScript + Node.js LTS + 官方 MCP TypeScript SDK，部署为一个无数据库服务：

- `GET /music`：轻量网页与原生 `<video>` 播放器；
- `GET /music/data/...`：小型、版本化的歌曲元数据与时间轴 JSON；
- `POST/GET /music/mcp`：MCP Streamable HTTP 入口；
- `GET /healthz`：不包含外部依赖的健康检查。

媒体文件不经过应用服务中转，放在独立对象存储/CDN。MP4 采用 iPhone Safari 普遍支持的 H.264/AAC 组合，网页使用 `controls`、`playsinline`、`preload="metadata"`，不强制有声自动播放。对象存储必须正确支持 Range、内容类型和缓存头。

歌曲元数据、歌词、演唱者、段落和音乐感知内容使用同一份版本化数据源，在构建阶段生成网页与 MCP 所需的只读产物，避免双份事实源。

### 3.2 MCP 设计

以稳定的 Streamable HTTP 协议版本和官方 SDK 为基线，实现初始化、能力协商、`tools/list` 和 `tools/call`。第一版只暴露四个只读工具：

- `music_catalog`
- `music_start`
- `music_next`
- `music_seek`

进度优先由客户端游标维护。游标只包含歌曲 ID、时间轴修订号和当前位置，不包含用户身份或敏感信息；服务端每次验证游标并返回新游标。这样不同客户端天然隔离，无需数据库或粘性会话，也支持重复调用、回听与重新开始。

每次只返回一个自然乐句或一个短段落，并同时提供精简文本 `content` 与机器可读 `structuredContent`。结果明确标注内容来源为人工标注、自动测量或模型推断，并声明这是预生成摘要或结构化特征，不代表模型直接接收了原始音频。

不在第一版提供原生音频内容块，不把音频能力当作跨客户端兼容前提。可以保留受控资源链接作为后续实验项。

协议参考：

- MCP Streamable HTTP 要求单一 HTTP endpoint，并定义 POST/GET、Origin 校验和可选会话：https://modelcontextprotocol.io/specification/2025-11-25/basic/transports
- MCP 初始化、能力与版本协商：https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle
- MCP 工具发现与调用：https://modelcontextprotocol.io/specification/2025-11-25/server/tools
- OpenAI 远程 MCP 文档确认 Responses API 可连接支持 Streamable HTTP 或旧 HTTP/SSE 的远程服务器：https://developers.openai.com/api/docs/guides/tools-connectors-mcp

跨 GPT、Claude、Gemini 的兼容性只能在实际客户端中分别验证，不能由协议实现直接推定。

## 4. `crotown.app/music` 路由方案

DNS 只能把主机名指向服务，不能按 URL path 分流。因此不能仅给 Railway 添加一条 DNS 记录来实现 `crotown.app/music`，也不应把整个 `crotown.app` 绑定到新 Railway 服务。

建议分两步：

1. 验收阶段：使用 Railway 临时域名，或经批准后使用独立子域名 `music.crotown.app`。该地址让项目在完全脱离迎风小镇主系统时仍可独立运行。
2. 正式阶段：由 `crotown.app` 当前入口层添加一条最小范围的反向代理规则，仅将 `/music` 和 `/music/*` 转发到独立服务；其他路径保持原样。代理必须保留方法与请求体，允许 MCP POST/GET 与流式响应，关闭不必要的响应缓冲，并把 `/music/mcp` 原样送达。

这条正式路由属于生产入口变更，必须先确认当前入口技术、回滚方式、超时和流式代理支持，再单独审批执行。该变更已于 2026-10-15 获批，并以仅匹配 `crotown.app/music*` 的独立 Cloudflare Worker 落地；实现、验收和回滚记录见 [domain-routing.md](domain-routing.md)。

Railway 官方文档说明自定义域名通过 DNS CNAME/TXT 接入，未将 URL path 作为 DNS 分流能力：https://docs.railway.com/networking/public-networking

## 5. A/B 成本与效果验证

评估阶段可以同时生成候选 A 与候选 B，但正式运行时必须二选一，不保留动态路由或自动降级。

### 5.1 共同基准

- 使用同一份最终母带、相同的乐句/段落边界和相同歌词版本；
- 先建立 12–20 个由人工校验的音乐事件作为参考答案；
- 设三组输入：仅歌词、歌词 + 预生成摘要、歌词 + 结构化声学特征；
- 使用固定问题集测试演唱者切换、强弱变化、乐器进入/退出、主副歌转换、节奏变化和段落关系；
- 评分以事实命中、漏报、误报和时间定位误差为主，不以回复是否优美为指标；
- 每组对多个模型和多个重复样本进行盲评。

### 5.2 候选 A：结构化声学特征

离线提取 RMS/响度、起音密度、节拍、音高轮廓、频谱与段落边界，再压缩为按乐句聚合的 JSON。乐器、人声关系等不能可靠地由基础特征直接证明的内容必须标记为模型推断或人工标注，不能包装成自动测量事实。

记录：离线处理时长、峰值内存、产物字节数、单段 token、全曲 token、网关序列化耗时，以及相对“仅歌词”的准确率提升。

### 5.3 候选 B：预生成音乐摘要

按同一时间轴制作简洁摘要，覆盖当前演唱者、歌词、主要乐器、可观察的人声/旋律/节奏变化和段落关系。每条字段保留来源标签与人工校对状态。

记录：自动初稿耗时、人工校对时长、产物字节数、单段 token、全曲 token、事实准确率和后续维护成本。

### 5.4 网关与 token 测试

- 用真实 MCP 响应分别测量工具定义、单次调用及完整推进一首歌的输入/输出 token；优先使用各模型 API 返回的 usage，另保存本地估算作交叉检查。
- 使用 1、5、20、50 并发的固定回放，记录吞吐、p50/p95/p99、CPU、内存、响应字节和错误率。
- 所有测试读取预生成只读文件，禁止在请求内运行音频分析。
- 初始返回大小目标应在拿到真实数据后由测量决定；在确认前不把任何高 token 方案定为正式架构。

首轮本地数据与成本代理测试、27 次跨模型对照及 MSS/0.3 三轮复测已经完成，详见 `docs/perception-ab-report.md`、`docs/mss-cross-model-eval-report.md` 与 `docs/mss-v0.3-eval-report.md`。最终选择候选 B：“预生成客观音乐摘要＋数值曲线”。MSS/0.3 虽达到最多 642 token、客观均分 9.89 / 10，但明确事实矛盾数没有通过预设安全门槛，因此只保留为研究产物。

## 8. 预期资源消耗（待素材实测）

- 应用服务：一个无数据库 Node.js 服务；预估 256–512 MB 内存即可作为首轮测试规格，实际以负载测试峰值为准。
- CPU：正常请求只做 JSON 校验、游标计算与静态读取；不包含在线音频分析，通常远低于媒体转码负载。
- 数据文件：预生成摘要通常为每首歌几十 KB 量级；结构化特征随时间分辨率可能增长到数百 KB 或更多，必须实测后决定。
- 媒体存储：当前已确认 MP4 与 MP3 合计约 37.7 MB；加上海报、版本冗余和后续产物后仍应按低于 100 MB 的首版静态素材预算规划，实际以最终上传物为准。
- 带宽：主要由 MV 播放决定，而不是 MCP；应按 MP4 码率 × 完整播放次数估算。
- MCP token：全曲 MSS/0.3 实测增量为 GPT 480、Claude 642、Gemini 642 token；正式 MCP 将按短段返回客观摘要，不重复注入全曲，单次与完整推进成本在工具实现后继续测量。
- 新增费用：OpenRouter 两阶段累计报告费用 `$0.21852794`；没有创建 Railway、对象存储或其他付费资源。
